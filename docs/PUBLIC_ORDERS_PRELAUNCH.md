# Public Orders pre-launch checklist

Public order confirmation email (SES) is **not wired in prod today**: `tofu/application/environments/prod/main.tf` does not instantiate the `ses` module, and the AppSync `public-orders` Lambda Role carries no SES grant there (see `modules/iam` `ses_order_emails_enabled`, default `false`). In that state the mailer honestly reports `configured: false` (`src/handlers/public_order_emails.py`, `_ses_config` returns `None` when any of `SES_ORDER_FROM_ADDRESS` / `SES_ORDER_TEMPLATE` / `SES_ORDER_SELLER_TEMPLATE` / `SITE_URL` is missing), so orders still succeed and the UI reports that no email was sent rather than implying success. Do not flip the feature flag before the SES slice below is green.

- [ ] **Instantiate the prod `ses` module slice.** Add a `module "ses"` block mirroring `tofu/application/environments/dev` (source `../../modules/ses`) with `environment = "prod"`, `zone_domain` = the prod-owned zone, and a production `subject_prefix` (empty, not `[DEV] `). Wire its outputs into the `iam` module: `ses_order_identity_arn = module.ses.identity_arn`, `ses_order_template_arns = module.ses.template_arns`, `ses_order_emails_enabled = true`. Also set the four env vars on the public-orders Lambda so `_ses_config()` returns a config. VERIFY the exact variable names and Lambda env wiring against the dev environment before copying.
- [ ] **Request SES production access for `kernelworx.app`.** Dev stays sandboxed by design (module comment). Production access must be requested for the `kernelworx.app` identity before arbitrary buyer recipients can receive mail. VERIFY current SES account sending limits/quota via `aws sesv2 get-account` before go-live.
- [ ] **DKIM / SPF merge rules — additive only.** The ses module creates only new records under a subdomain (`orders.<zone>`) and never edits the apex. When merging any DNS change: add new records only; add new MX records only at a *worse* (higher number) priority than any existing MX; never overwrite or remove a pre-existing record; read the apex zone (current records and their values) before any `tofu apply` that touches DNS.
- [ ] **DNS apex read before apply.** Run `tofu plan` and inspect every `aws_route53_record` add against the live zone; abort if any record is a replacement/delete of an existing name. Managed DKIM CNAMEs under `orders.*` are net-new by construction.
- [x] **Lambda concurrency cap removed (captain's ruling, Option A).** `reserved_concurrent_executions` was dropped from the public-orders function: AWS requires the account's unreserved concurrency to stay at or above 100, and this account's `ConcurrentExecutions` quota is too low to reserve any amount. The flood guard is `throttle_public_order_create_fn.js` (5 creates/min per share token, already pipeline step 3); if the account quota is ever raised via Service Quotas, restoring a cap is a one-line change in `tofu/application/modules/lambda/main.tf`.
- [ ] **Switch-flip order.** 1. Provision prod SES (module + IAM + env vars) and confirm `tofu plan` green. 2. Request/confirm SES production access. 3. Verify DKIM records and send a test. 4. Only then enable the feature flag / public-order email path for prod traffic.

Anything above marked VERIFY must be confirmed against the live terraform state and AWS account before execution; do not assert values not present in the code today.
